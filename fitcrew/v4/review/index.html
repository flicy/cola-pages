S1 · 产品总览

一个 AI 健康实验伙伴，不是一个数据仪表盘

FitClew 的产品骨架是四层时间结构：越靠近"现在"，动作越具体；越靠近"90 天"，认知越结构化。所有判断都来自「AI 提假设 → 用户授权 → 观察 → 验证 → 学习」的实验循环，而不是直接给健康评分。

四层时间结构（数据模型 → 界面的映射）

90 Day Journey长期方向与阶段
数据实体 Journey
→
This Week Experiment本周在验证的假设
数据实体 Experiment
→
Today Mission今天唯一主行动
数据实体 Mission
→
Right Now Action实时策略结果
短期计算不落第二库

对应五 Tab：今天 = Mission + Right Now ｜ 旅程 = Journey ｜ 实验 = Experiment ｜ 记录 = 主观输入（Body Check / 精力 / 睡眠感受）｜ 我的 = 授权与数据控制

AI Native 主循环

AI 提假设基于授权聚合数据 + 用户目标，提出低风险个人实验
→
用户授权看到假设、读取类别、观察指标、停止条件后才开始
→
AI 观察 → 验证 → 学习Observation → ExperimentResult → 确认后的 Memory/Insight → 下一个实验

产品红线（写进交互合同的）

无数据不生成分数或结论
不做羞耻、扣分、连续打卡惩罚
健康判断必须展示数据时间窗、质量和限制
授权、同步、ClawBot、删除显示真实状态，不做装饰性假开关
首发排除：餐食照片识别、医疗诊断、模型直读原始健康数据
S2 · 全局旅程

从启动到可用：注册只是第一站，授权才是门槛

全局状态机决定用户看到什么。健康内容在完成 HealthKit 授权前一律不展示——这是与读手表 Insight 最大的结构差异之一（详见 S9 对标）。

→
Onboarding O1–O6价值边界→90天方向
→数据用途→授权→首同步→Body Check
→
首次同步持续或暂停
行为必须明确
→

restricted / failed / ready完整

Onboarding 六步可中断可恢复：重启 App 回到最近未完成步骤，已完成步骤不重复。

展示类别与用途 → 开始同步 → Today 完整态
部分允许
显示可用/缺失项 → 同步可用类别 → baseline_building

S3 · 页面一「今天」

每日行动中心：一个视口，一个判断，一个动作

Today 是全产品的枢纽。它不展示数据海洋，只回答三个问题：我现在什么状态、下一步做什么、为什么。

01页面区块结构（自上而下）

1Current State当前状态文字 + 证据时间窗 + 数据质量标识
2One Next Move今天唯一主行动，三个出口：完成 / 调轻 / 跳过
3Why数据来源 + 局限说明，判断可追溯
4Active Experiment进行中实验的当前状态 + 停止入口
5Next Check下次重新评估的条件（不是日期，是条件）
6Body Check 入口主观感受快速记录（Demo 里已做成白卡情绪选择器）

02Mission 写入流（幂等，防重复提交）

完成按钮立即禁用 → 提交中
成功显示时间与审计确认
／
调轻Sheet 给 2–3 个允许的替代方案
说明仍在观察什么 · 关闭不写入
／
跳过原因可选 · 无扣分无羞耻文案
服务端幂等键防重复记录

03四态与 Demo 差距

状态用户看到状态
ready状态 + 时间窗 + 质量 + 下一步 + WhyDemo 仅完整态
baseline_building已有输入、缺口、预计时间、低负担行动，不给分数Demo 未实现
restricted授权限制说明 + 手动记录 + 数据用途入口Demo 未实现
failed失败归因 + 本地保存状态 + 重试，不用"AI 思考中"掩盖Demo 未实现
S4 · 页面二「旅程」

90 天方向感：先看阶段，再看趋势

旅程页回答"我朝我的方向走了多远"。规则：先显示 90 天方向与当前阶段，再展示趋势——顺序不能反。

01区块结构

1方向与阶段90 天方向 + 当前所处阶段（Onboarding O2 选定，可后补）
2时间窗切换30 / 60 / 90 天；每次切换保留来源、质量和缺口说明
3趋势图点击图表 → 文字摘要 + 范围 + 缺口 + 相关实验事件
4里程碑日期 + 证据 + 相关行动 + 可撤回/删除状态

02硬规则

趋势线不得跨越数据缺口伪造连续性
＋
数据不足时用用户反馈和实验时间线解释
＋
不放空 KPI 卡充数

03Demo 差距

部分Demo 有趋势视觉与阶段卡，缺 30/60/90 切换的缺口说明联动
未实现里程碑的撤回/删除状态；点击图表的文字摘要浮层
S5 · 页面三「实验」

产品的灵魂：假设制实验，授权后才跑

这是 FitClew 与所有健康 App 的本质区别——AI 不直接下结论，而是提案一个可停止的低风险实验，用户授权后才开始观察。

01列表结构：三组

进行中 Active
·
等待决定 Proposed
·
已完成 Completed

卡片只显示：名称、目的、一句状态、进入详情的动作。完整指标只在详情展示。

02实验状态机

proposed
→
authorised用户看过四要素后授权
→
active
→
analysing
→
completed
paused 暂停
stopped 停止需确认影响；停止后派生结果按规则失效或删除
rejected 拒绝提案
completed → user_feedback → 确认后的记忆

03授权 Sheet 必须可见的四要素

1假设与干预行为这个实验到底在验证什么
2读取类别与窗口读什么数据、purpose、基线窗与实验窗
3观察指标与门槛看哪些指标、质量门槛、不确定性
4成功/停止/删除规则什么算成功、何时停、数据保留与删除

04Demo 差距

部分三组列表已有；缺 Proposed 卡片的授权入口与 Sheet 四要素
未实现暂停/停止的影响确认流；结果页的用户反馈与"确认记忆"
S6 · 页面四「记录」

结构化主观输入：五类，全部可撤回

记录页是 AI 观察数据之外的主观信号源。设计原则：结构化选择优先，不给模型自由文本，默认不存为长期记忆。

01五类记录

类型输入成功后
精力五级文字标签保存时间 + 当天撤回入口
睡眠感受简短选项 + 可选标签结构化保存，不默认成长期记忆
压力低/中/高 + 可选来源可撤回；无自由文本
训练感受完成/偏累/恢复良好/暂不记录可关联当日 Mission
不适停止信号明确结构化选择提示停止实验 + 寻求专业帮助边界，不诊断

02写入状态机（每一条）

保存中
→
成功显示时间 + 撤回入口
／
失败保留已选内容 · 防重复点击
服务端幂等 · 可重试

03Demo 差距

已实现情绪选择器（Body Check 雏形）白卡交互
未实现五类记录的完整入口；撤回流；失败重试态
S7 · 页面五「我的」

数据主权页：授权、导出、删除、ClawBot

这一页是信任的锚。所有状态真实可见，所有破坏性操作有二次确认和证据回执。

01数据源与授权

·Apple Health显示获准类别、最近同步、限制、每项 purpose
·撤回单项授权先说明：哪些读取停止、哪些派生结果失效、数据何时删除
·同步状态区分同步中/成功/延迟/失败；用户可主动同步

02导出 / 删除 / 注销

导出选范围 → 生成 → 安全分享
·
删数据选范围 → 影响说明 → 二次确认 → 进度 → 证据
·
注销影响说明 → 二次确认 → 撤会话/同步/实验/ClawBot → 证据

03微信 ClawBot 连接（六态）

off
→
disclosure提醒类型/排除内容/静默时段
→
binding_pending官方绑定步骤可取消
→
connected偏好配置 · 发送记录

只发送用户明确选择的待办摘要；不发原始健康数值、诊断、自由文本。无官方通道时只显示未连接或 dry-run，不伪称已发送。

04Demo 差距

部分页面骨架已有；缺授权明细与 purpose 展示
未实现ClawBot 六态连接流；导出/删除的证据回执
S8 · 注册登录（今晚新增议题）

微信登录为主，Apple 登录兜底合规，邮箱殿后

Chris 建议：注册用微信。微信登录后天然衔接 ClawBot 待办提醒（发微信提醒今日 Mission）。但 iOS 审核有硬约束：提供第三方登录的 App 通常须同时提供 Sign in with Apple（Guideline 4.8）。

方案 A · 微信优先（建议采纳）

微信一键登录App 拉起微信授权 → 手机号可选补充
→
自动创建账号 + 微信 OpenID 绑定unionid 留扩展（公众号/小程序触达）
→
进入 OnboardingClawBot 在「我的」里可一键升级绑定（已持有微信身份，绑定成本低）

优势：转化路径最短、ClawBot 提醒闭环天然成立、目标用户（健康 App 用户）微信渗透率≈100%。

合规与兜底

1Sign in with Apple与微信并列展示（审核 4.8 要求），隐私型用户走这条路
2邮箱注册殿后入口（折叠），服务海外版 InsyHealth 式扩展
3会话恢复微信静默续期；Apple/邮箱走系统级恢复
4注销注销账号必须同时解绑微信 OpenID 并删除云端数据（审核 + 信任双要求）

登录 → ClawBot 提醒闭环（产品差异点）

微信登录
→
Onboarding 完成
→
「我的」开启 ClawBotdisclosure：只发待办摘要
→
微信收到今日 Mission 提醒点回 App 完成 → 数据进实验循环
S9 · 对标：读手表 Insight

同赛道验证了需求，我们的差异在"实验制"

读手表 Insight（insyhealth.com，App Store 4.6 分 200+ 评分）验证了「Apple Watch 数据 AI 解读」的需求真实存在。四模块对照（升级版：完整产品拆解已按 EnglishFlow 框架重做，见 读手表 Insight · 产品拆解）：

模块读手表 Insight 的做法FitClew 的做法与差异
注册授权 Apple Health 系统授权为主；官网 FAQ 强调"本地分析、数据是否上传"的隐私问答；登录方式官网未明示 微信登录优先（S8）＋ 授权前强制"数据用途说明"（O3）＋ 授权四分支状态机。更重：把授权做成产品能力而非系统弹窗
数据采集 HealthKit 读睡眠/心率/HRV/运动/身体成分；Apple Watch 表盘复杂功能（抬腕看电量+压力+恢复） 同一数据源；首发不做表盘（排期内）。可借鉴：表盘是它最聪明的留存抓手，V1.1 可评估
数据分析 四维度：身体年龄评估 / 睡眠恢复（阶段占比+趋势+异常提示）/ 身体电量 0–100 / HRV 压力曲线 不直接给分数结论；以实验制观察（假设→授权→验证）。根本差异：它给答案，我们给验证过程；"身体年龄"锚点指标值得借鉴为 Journey 阶段目标
数据洞察 月度健康画像（30 天节律报告）+ 规律识别（工作日 vs 周末）+ AI 对话式解读 Journey 页 30/60/90 趋势 + 里程碑 + 实验结果归档。可借鉴：月度画像的报告形态；AI 对话解读在首发排除清单外可排 V1.1
商业化 免费（当日数据）/ Pro（趋势+月度分析）/ Pro Max（个性化方案+预测）；健康币体系；小红书矩阵招募冷启动 付费墙未定（今晚议题 Q6）。它的三级分层（当日免费/趋势收费/方案更贵）是健康类验证过的结构

它的增长打法（对 Build in Public 的参考）

小红书账号矩阵 30+ 篇招募帖（"急招刚买 S11 的用户""找 iWatch 戴满 3 年的人来挑错"），把冷启动做成了连续剧；"身体年龄 Agent 公测"作为事件节点。FitClew 的 8/24 首篇可以直接借"招募共创"叙事，而不是纯产品介绍。

S10 · 今晚逐项对齐

待决策清单：10 个问题定边界

按优先级排序，每条都直接改变 Demo 下一版的范围。

Q1
注册登录走方案 A（微信优先 + Apple 兜底）吗？
定了就补 Demo 的登录页与 Onboarding 前置流程（当前 Demo 直接进主页）。
Q2
Today 四态今晚先做哪个？
建议 baseline_building（新用户前 7 天都会处在这个态，比 ready 更早被看到）。
Q3
Mission 的"调轻"替代方案给哪 2–3 个？
需要按真实 Mission 类型定义规则（如"30 分钟力量"→"15 分钟"或"改约明天"）。
Q4
实验授权 Sheet 的四要素展示顺序与文案口径
这是产品灵魂页，建议逐字过一遍。
Q5
记录页五类入口的信息架构
五类平铺还是按"当下记录 / 复盘记录"分组？
Q6
付费墙结构（对标它的免费/Pro/Pro Max）
建议先定"什么免费"：当日 Mission + Body Check 免费，趋势与实验结果收费。
Q7
ClawBot 提醒的内容边界确认
规格是"仅待办摘要"——要不要加"实验结果通知"？涉及隐私口径。
Q8
"身体年龄"要不要作为 Journey 锚点指标
对标产品用它做了公测事件，传播性强；但医疗边界文案要跟。
Q9
表盘复杂功能排不排进 V1.1
它最聪明的留存抓手，但需要 watchOS 开发资源。
Q10
Demo 下一版的验收形态
继续 Web Demo 补状态，还是直接 SwiftUI 原型接上？（关联 task #27）
